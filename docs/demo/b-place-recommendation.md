B는 백엔드 개발자다. 프론트 컴포넌트·배지·상세 화면 수정, API 호출 연결, 배포 설정은 SeokH-dev 담당이다. B는 화면에서 필요한 서버 정보와 계약을 제공하고 연결 예시를 전달한다.

### 진행·결과 전달

1. 각 항목에 `기존 API로 충족 / 백엔드 수정 가능 / 사용자 결정 필요 / 불가·데이터 의존`과 구체적 서버 작업을 기록한다. “가능”만 답하지 않는다.
2. 수정 가능한 항목은 본인 브랜치에서 이어서 구현한다. 일부 운영 정책이 미정이면 필요한 질문·데이터를 기록하고 독립적인 다른 구현은 진행한다. 미확정 기준을 임의로 하드코딩하지 않는다.
3. 기존 API로 충족하면 요청·응답 예시와 필드의 의미를 남기고 불필요한 새 API는 추가하지 않는다.
4. 추가 필드·인증·빈값·실패 응답·기존 클라이언트 호환을 Swagger와 문서에 반영한다. DB 변경이 필요하면 기존 Flyway 수정 없이 새 버전을 추가한다.
5. 관련 PostgreSQL 통합·회귀 테스트를 실행하고 구현 PR에 최종 계약·검증 결과·프론트 연결 방법을 남긴다. 이 문서 PR의 승인만으로 기능 완료를 표시하지 않는다.
6. 데이터 미확보·기술 제약으로 불가하면 이유와 필요한 데이터/결정을 기록한다. 범위 축소와 제품 정책 변경은 사용자에게 확인한다.

## B-01 연령 적합성 표시

**화면 근거:** [맞춤 장소 목록](https://www.figma.com/design/lWZGGaQay5Wcp7wKw6YEze/?node-id=143-1807)과 [장소 상세](https://www.figma.com/design/lWZGGaQay5Wcp7wKw6YEze/?node-id=143-1986)의 `7세 적합`.

**현재:** `POST /api/recommendations`는 선택 아이의 관심사와 책 장르를 점수에 사용하지만 연령대를 사용하지 않는다. `RecommendationResponses.MatchedCondition`은 `AGE`를 허용하지만 실제 생성은 없다. `Place.targetAgeInfo`는 자유 텍스트이고 아이는 정확한 나이가 아닌 `ageBandCode`를 저장한다.

근거 코드:

- [추천 계산](../../src/main/java/com/podo/server/recommendation/service/RecommendationService.java)
- [추천 요청·응답](../../src/main/java/com/podo/server/recommendation/web/RecommendationResponses.java)
- [장소 데이터](../../src/main/java/com/podo/server/place/domain/Place.java)
- [아이 프로필](../../src/main/java/com/podo/server/profile/domain/ChildProfile.java)

**B 리뷰 요청:** 검수된 장소 연령 데이터와 선택 아이 연령대를 비교하여 `matchedConditions.kind=AGE`로 적합 근거를 반환할 수 있는지 검토한다. 기존 추천 API 확장을 우선 검토하며 별도 연령 추천 API를 먼저 만들지 않는다.

**사용자 담당 선행 결정:** 장소 적합 연령의 운영 데이터 형식, 연령대 겹침 시 적합 판정, 미확인 표현을 정한다. 자유 텍스트에서 숫자를 임의 파싱하거나 `6~7세`를 정확히 `7세`로 표시하지 않는다. 실제 저장된 라벨에 맞는 문구를 사용한다.

**계약 제안:** 기존 `childProfileId`로 연령대를 해석하고, 근거가 확인된 경우에만 AGE 조건을 반환한다. 정확한 `code/label` 형식은 운영 목록과 함께 리뷰에서 확정한다. 후보 제외·순위 변경은 배지 제공과 별개 정책이므로 이 문서로 확정하지 않는다.

**수용 기준:**

- [ ] 아이 연령대와 장소의 검수된 연령 정보가 적합할 때만 AGE 근거를 반환한다.
- [ ] 프로필 없음·연령 없음·장소 연령 미확인 시 적합 배지를 임의 생성하지 않는다.
- [ ] 타 계정 프로필은 기존 소유권 검증으로 차단한다.
- [ ] 관심사·목적·날씨 규칙, 최대 5곳과 후보 부족 이유는 합의 없는 변경을 하지 않는다.
- [ ] 프로필을 수정한 뒤 새 추천에는 새 정보가 적용된다. 과거 방문·퀴즈는 변경하지 않는다.
- [ ] 운영 데이터와 API 스키마, 관련 통합 테스트를 함께 검증한다.

## B-02 장소 상세의 맞춤 조건

**화면 근거:** 장소 상세 `143:1986`의 `하늘이와 맞는 조건`, `곤충 관심`, `7세 적합`, `맑은 날 야외`.

**현재:** 추천 응답에는 `matchedConditions`가 있다. 상세 API는 `visitDate`를 받지만 개인화 조건은 반환하지 않는다. 프론트 `src/pages/PlaceDetail.tsx`는 추천 화면에서 받은 이동 상태가 있으면 조건을 사용하고, 직접 진입하면 장소 주요 활동을 대신 사용한다. 따라서 상세 API 전체가 미구현인 것은 아니며 진입 경로별 표시 차이가 문제다.

**사용자 담당:** 직접 URL·지도·인기에서 들어왔을 때도 같은 아이 기준 조건이 필요한지, 방문일과 선택 프로필을 어디서 전달할지 통합안을 정한다.

**B 리뷰 요청:** 기존 추천 조건 계산을 특정 장소에 재사용할 수 있는지, 상세 조회를 확장한다면 인증·프로필 소유권·기존 공개 조회에 어떤 영향을 주는지 확인한다. `childProfileId`를 상세에 추가하는 안과 프론트에서 검증된 조건을 조합하는 안은 아직 선택하지 않았다. 동일 조건 산출을 위해 추천 상위 5곳에 특정 장소가 포함되어야만 하는 구조는 피한다.

**수용 기준:**

- [ ] 지도·인기·추천·새로고침으로 같은 장소에 들어갈 때 조건의 의미가 일치한다.
- [ ] 맞춤 근거가 없을 때 일반 장소 활동을 개인화 근거처럼 표현하지 않는다.
- [ ] 비로그인·프로필 생략·타인 프로필·날씨 조회 실패의 응답을 정의한다.
- [ ] 프로필·방문일 변경 후 이전 조건이 남지 않는다.

## B-03 기존 API로 제공되는 항목과 데이터 확인

운영시간·요금·대상 연령 안내·편의시설·주의사항·출처·지도 링크는 [PlaceResponses](../../src/main/java/com/podo/server/place/web/PlaceResponses.java)에 이미 있다. 새 API를 만들기보다 데모 장소의 실제 데이터와 화면 표시를 확인한다. 데이터가 없는 경우 확인된 사실처럼 채우지 않는다. 날짜별 영업 가능 여부를 계산하는 기능이 있다고 가정하지 않는다.

인기는 현재 전체 상위 15곳을 반환한다. Figma 홈의 `카테고리별 15곳` 문구는 카테고리마다 15개를 뜻하는지 모호하며 이전 PRD는 전체 상위 15곳 내 화면 필터를 명시했다. **현재 서버를 오류 또는 미구현으로 분류하지 않는다.** 문구 해석은 사용자 담당으로 남기고, 별도 카테고리 인기 API는 이번에 요청하지 않는다.

기온·미세먼지·체험 소요시간·도서는 [사용자 담당](ownership.md)이다. B에게는 기존 장소·날씨 계약에 미치는 영향만 리뷰를 요청한다.
