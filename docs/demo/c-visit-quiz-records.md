# C파트: 방문·퀴즈·기록 변경 검토 가이드

리뷰 요청: `jinyoung02` · [담당 기준](ownership.md) · 기준 서버 `00297d0`

현재 방문·퀴즈·완료 지도·사진 생성 API는 이미 구현되어 있다. 이 문서는 기존 계약으로 화면을 재현할 수 있는지와 확장이 필요한 경계를 검토한다. 정책과 파트가 애매한 사항은 사용자 담당으로 정한다.

## C-01 마이 탐험 카드와 기록 다시보기

**화면 근거:** [마이페이지](https://www.figma.com/design/lWZGGaQay5Wcp7wKw6YEze/?node-id=209-256)는 장소명·활동 제목·날짜를 표시한다. [지도 탐색](https://www.figma.com/design/lWZGGaQay5Wcp7wKw6YEze/?node-id=215-601)에는 `기록 다시보기`가 있다.

**현재:** [VisitResponse](../../src/main/java/com/podo/server/visit/web/VisitResponse.java)는 방문 날짜·완료 시각·장소·퀴즈 세트·진행 수치를 반환한다. [CompletedPlaceResponse](../../src/main/java/com/podo/server/visit/web/CompletedPlaceResponse.java)는 장소 단위 집계다. 방문 응답에 활동 제목은 없지만, 프론트 `src/pages/MyPage.tsx`는 장소 `mainActivities[0]`와 완료 방문·완료 장소 데이터를 조합하므로 새 API가 무조건 필요한 것은 아니다.

**사용자 담당 결정:** 카드 제목이 장소 대표 활동인지 완료한 퀴즈의 제목인지, 날짜가 방문 예정일인지 완료일인지, 같은 장소 재방문을 카드 한 장으로 묶는지 방문마다 보여주는지를 정한다. 현재 선택 아이와 가족 전체 기록의 관계도 화면 의도에 맞게 확인한다. 임의 레벨·칭호를 신규 요구로 추가하지 않는다.

**C 리뷰 요청:** 기존 `GET /api/visits?status=COMPLETED&placeId=...`와 방문 상세·퀴즈 조회로 정해진 카드를 구성할 수 있는지 확인한다. 부족하면 완료 방문 응답에 저장된 활동/퀴즈 요약을 추가하는 안을 검토하되 별도 탐험카드 API를 먼저 만들지 않는다. 과거 기록 제목을 현재 장소 활동으로 대체해도 되는지는 사용자 결정 후 확장한다.

현재 방문 커서는 생성 시각 기준이므로 `최신 완료 기록`과 같은 뜻이 아니다. 최신 완료 시각 기준 선택이 필요하면 프론트에서 필요한 범위를 읽어 선택할지 서버 정렬/조회 확장을 할지 합의한다. 첫 페이지의 첫 항목을 무조건 최신 완료로 간주하지 않는다.

**수용 기준:**

- [ ] 같은 장소를 두 번 완료하고 다른 아이/프로필 없음으로 완료한 사례의 카드·지도 표시를 합의한다.
- [ ] `기록 다시보기`가 선택한 본인 방문의 실제 퀴즈·답변·힌트 기록을 연다.
- [ ] 생성일과 완료일이 역전된 두 방문에서도 합의한 정렬과 기록 선택이 맞는다.
- [ ] 페이지가 여러 개일 때 누락·중복이나 최신 기록 오선택이 없다.
- [ ] 장소 비공개·정보 변경·빈 활동 제목·프로필 수정 후에도 과거 기록의 의미가 유지된다.
- [ ] 장소별 집계와 방문별 기록의 개수를 혼동하지 않는다.

## C-02 미션 제목과 진행 표시

**화면 근거:** [미션](https://www.figma.com/design/lWZGGaQay5Wcp7wKw6YEze/?node-id=209-412)의 짧은 미션명, 완료/진행중/잠김, `2/3`, 진행률과 현장 힌트.

**현재:** [QuizResponses](../../src/main/java/com/podo/server/quiz/web/QuizResponses.java)에 순서·질문·관찰 안내·응답 여부·힌트 열람 단계·진행 수치가 있다. 별도 짧은 미션명 필드는 없다. 힌트 본문은 열람 API로 받아 열람 수를 기록한다.

**C 리뷰 요청:** `observationGuide`가 짧은 미션명과 관찰 장소를 표현하기에 충분한지 검토한다. 부족하면 운영 콘텐츠의 짧은 제목을 추가하는 안을 검토한다. 프론트에서 문제 문장을 임의로 요약하거나 다른 장소에 안내판·전시관을 고정 표시하지 않는다. 별도 필드 추가 여부는 사용자와 의미를 확정한 뒤 정한다.

**수용 기준:** 진행률은 3문항 응답 수로 일관되게 계산하고 정답 수와 혼동하지 않는다. 미열람 힌트를 미션 화면에서 미리 노출해 기록을 우회하지 않는다. 재접속 시 상태·순서·기존 답변을 유지하며 위치 인증을 미션 잠금 조건으로 추가하지 않는다. 힌트 수가 버튼 탭 수인지 고유 단계 열람 수인지 화면 문구를 기존 API 의미에 맞춘다.

## C-03 고학년·연령별 퀴즈

**화면 근거:** [탐험 시작](https://www.figma.com/design/lWZGGaQay5Wcp7wKw6YEze/?node-id=143-1781)의 `고학년 퀴즈`, 연령 난이도 메모 `410:7128`.

**현재:** [ObservationAi.Input](../../src/main/java/com/podo/server/observation/ai/ObservationAi.java)은 장소명·사진·근거를 전달하고, [QuizSet](../../src/main/java/com/podo/server/quiz/domain/QuizSet.java)에는 난이도 필드가 없다. 연령별 생성·세트 선택은 지원한다고 볼 수 없다.

**사용자 담당 결정:** 고학년 버튼이 별도 난이도 선택인지, 프로필 연령대 자동 적용인지, 프로필 없는 경우의 기본값과 연령대별 표현 기준을 먼저 정한다. 기존 PRD의 진행 중 고정 문항 정책과 충돌하지 않도록 합의한다.

**C 리뷰 요청:** 결정된 범위를 기존 사진 생성 입력과 공용 세트 선택 중 어디에 적용해야 하는지 영향 범위를 검토한다. 난이도를 위해 별도 퀴즈 API를 만들기 전에 기존 계약 확장 가능성을 확인한다.

**구현 선택 시 수용 기준:** 생성·시작 시 선택한 기준을 고정해 새로고침·프로필 수정으로 진행 중 질문과 답이 바뀌지 않는다. 아이 별칭·계정 정보는 생성에 불필요하므로 모델에 보내지 않는다. 기본값·기존 세트·정정 재시작과의 호환을 정의한다. 실제 쉬운/고학년 콘텐츠 검수를 실행 테스트와 구분한다.

## C-04 오답의 ‘다시 한 번 더’

**화면 근거:** [오답 확인](https://www.figma.com/design/lWZGGaQay5Wcp7wKw6YEze/?node-id=386-6137).

현재 [QuizService](../../src/main/java/com/podo/server/quiz/service/QuizService.java)는 첫 답을 유지하고 다른 답 재제출은 `ANSWER_ALREADY_SUBMITTED`로 거절한다. 프론트 `src/pages/visit/QuizQuestion.tsx`는 오답 이후 연습을 화면 안에서 처리한다. `/quiz/restart`는 정상 진행 초기화가 아닌 오류 정정 복구 기능이다.

**C 리뷰 요청:** 화면 연습이 서버 점수·답안·완료 상태를 바꾸지 않는 현재 흐름을 확인한다. Figma 버튼만으로 재채점·점수 덮어쓰기를 요구한다고 해석하지 않는다. 재채점이 필요하다는 결정은 아직 없으며 추가 정책이 필요하면 사용자 담당으로 돌린다.

**수용 기준:** 오답 후 연습·새로고침·재접속에서도 첫 답/정답 수가 임의 변경되지 않는다. 같은 답 재전송은 중복 집계하지 않고, 3문항 모두 응답한 뒤에만 완료된다. 0개 정답이어도 완료할 수 있다.

## C-05 사진 생성 API의 연동 계약 확인

사진 프론트 연동·자동 공개 설정·실환경 시험은 사용자 담당이다. C에게는 기존 구현의 아래 계약과 제약이 맞는지 리뷰를 요청한다.

| 단계 | 기존 계약 및 주의점 |
|---|---|
| 업로드 | `POST /api/visits/{visitId}/observations`, multipart `files` 1~3장, 각 최대 5MiB, `Idempotency-Key`. 원본 File을 전송하고 같은 업로드 재전송은 키를 재사용 |
| 생성 | `UPLOADED/GENERATING/READY/FAILED`. READY만으로 시작하지 않고 `startAvailable=true` 확인 |
| 시작 | 기존 `POST /api/visits/{visitId}/report` 후 퀴즈 조회. report는 방문 위치 인증이 아님 |
| 재접속 | `GET .../observations/latest`로 기존 작업 복원. 중복 업로드로 새 작업을 불필요하게 만들지 않음 |
| 실패 | `retryAvailable=true`일 때 `POST .../{observationId}/retry`와 `expectedAttempt` 사용. 나머지 실패의 안내·대체 흐름은 사용자 담당 |
| 사진 표시 | 개인 사진은 Bearer 인증 조회이므로 일반 img src만 사용하지 않고 인증 fetch 후 표시 |
| 공개 | 서버 자동 검사를 통과한 결과를 즉시 공개하도록 설정. 수동 관리자 검수 API를 추가하지 않음 |

**필수 제약:** 사진만 있으면 모든 장소에서 생성되는 것은 아니다. [ObservationService](../../src/main/java/com/podo/server/observation/service/ObservationService.java)의 공식 근거 조건이 없으면 `SOURCE_NOT_READY`다. 업로드 전부터 사진을 건너뛰면 공용 공개 퀴즈를 사용할 수 있지만, 이미 업로드한 최신 작업이 실패했다면 report는 이를 기준으로 막는다. 실패 후 공용 퀴즈로 자동 전환하는 새 요구는 Figma에서 확인되지 않았으며 이번에 추가하지 않는다.

**검증:** [ObservationIntegrationTests](../../src/test/java/com/podo/server/observation/ObservationIntegrationTests.java)의 업로드·멱등성·타 계정 사진 차단·기존 퀴즈 연결·구 작업 덮어쓰기 차단 기준을 유지한다. 사용자 담당 E2E는 실제 데모 장소에서 업로드 → 자동 생성·공개 → 시작 → 3문항 완료 → 지도·기록 확인까지 수행한다. 기본 설정과 실제 운영값, 모델 키 준비 여부는 구별해서 기록한다.

## 리뷰에 남길 답변

- C-01/02: 현재 응답의 조합으로 충족 가능한 범위, 추가 콘텐츠 필드가 필요한 부분
- C-03/04: 기존 퀴즈 불변성·채점·정정 계약과 충돌하는 정책
- C-05: 상태·재시도·근거 데이터·사진 인증 계약의 정정 사항

문항·힌트·결과 수치·완료 지도 집계는 기존 구현이 있으므로 신규 API 목록에 중복 등록하지 않는다. API 경로·새 필드·데이터 변경은 리뷰 후 별도 구현 계획에서 확정한다.
